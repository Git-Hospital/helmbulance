## Where the documents agree and where they do not

The architecture and the research agree on the method:
- reproduced or not reported;
- control before treatment;
- Helm and kind as commands;
- no hosted service;
- Argo CD named for `lookup`.

They differ on one thing: **when Helmbulance starts contributing upstream.**
- **Architecture §8 and the README:** "running against popular community charts and sending fixes upstream" comes *later*, after v0.3.
- **Research:** success is measured in merged upstream fixes, and the cheapest proof is not a scan. It is reproducing a few *known, open* chart issues with the tool and offering the reproduction to the maintainers. That needs neither scan mode nor the hardened mode, only a safe way to run a handful of well-known charts.

### D3. How do the known-bug corpus charts run before the hardened mode exists?
The corpus uses community charts, which are third-party charts under §4.
- [ ] One GitHub Actions job per chart: a fresh VM, `permissions: {}`, no secrets, no caches, pinned chart versions. Old Bitnami versions will likely need `bitnamilegacy` image overrides. *(proposed)*
- [ ] Locally inside a VM with no host mounts.
- [ ] Wait for v0.3.

### D4. What is a failed treatment step?
The review (M2) shows that a chart refusing safely and an upgrade that really breaks both end up INCONCLUSIVE today.
- [ ] Split them. *(proposed)*
  - A refusal at render time (`required`, `fail`) is `PASS` with the note "refuses safely" and the message.
  - A failure after render (apply, rollout, crash) is `FAIL` with evidence.
  - Only a setup, timeout or environment failure stays `INCONCLUSIVE`.
  - A treatment failure is `FAIL` only when the control upgrade succeeded.
  - The report keeps a machine-readable `outcome: refused` next to the verdict.
  - Architecture §2 ("a failed install or upgrade is `INCONCLUSIVE`") is updated to match.
- [ ] Add a fourth verdict, `SAFE-REFUSAL`.
- [ ] Keep the current behaviour.

### D5. Severity of Secret drift
- [ ] Severities: *(proposed)*

  - TLS material as its own class;
  - an `expectedRotation` list in Helmbulance's own configuration, not in the chart's values (an unknown values key can fail `values.schema.json`).

## Plan for two people

Both of us write code, in separate files, and review each other's PRs. This follows Ege's proposal of 11 October.

**Roles:**
- **Ege: the CLI and the scenarios** (`cmd/`, `internal/`).

  - next, in the engine: the blockers, M1, D4, D5, `reinstall`, `gitops-render`.
- **Kadirhan: CI and the GitHub Action** (`.github/`, `action.yml`).
  1. Helmbulance's own CI. On every pull request: `go vet` and `go test`, then a kind job that runs every fixture pair in `testdata/charts/` and checks the exit codes (0 clean, 1 findings, 3 incomplete). The defective chart must FAIL and its fixed twin must PASS. This closes M5.
  2. A composite Action for users. It builds Helmbulance, runs it on `./chart` and writes `report.md` to the job summary.
  - Both follow §4's CI row:
    - `pull_request` only, never `pull_request_target`;
    - `contents: read`;
    - `persist-credentials: false`;
    - actions pinned by commit SHA;
    - no secrets, no caches.
  - Kadirhan also owns the corpus file and the outbound gate.

## Working agreement

- **Code changes:** every one goes through a PR, small and with a test. The other developer reviews; the author merges.
- **Upstream:** whoever wrote a reproduction posts it; the other checks the text against the gate first.
- **The outbound gate:** nothing goes upstream unless it:
  - was reproduced twice on a fresh cluster;
  - is still present in the chart's latest version;
  - is not documented as intended behaviour;
  - has no duplicate open;
  - follows the target's CONTRIBUTING file;
  - discloses tool and AI use in the issue or PR text, where the target project asks for it.
- **Security-class results:** these go privately, through GitHub private vulnerability reporting or the project's SECURITY.md. They are never published in a public issue or in this repository before the fix.
- **Open threads:** at most three open upstream threads at a time.
