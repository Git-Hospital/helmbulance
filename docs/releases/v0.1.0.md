# Helmbulance v0.1.0

The first release. Helmbulance installs a Helm chart into a throwaway kind cluster, runs day-two situations against the live release, and reports only what the cluster reproduced, with the evidence, the impact, a fix and the commands that reproduce it.

## Install

```sh
go install github.com/Git-Hospital/helmbulance/cmd/helmbulance@v0.1.0
```

It needs Go 1.27.2 (`go.mod`). A run also needs Docker, [kind](https://kind.sigs.k8s.io/), helm and kubectl on `PATH`; `test` and `matrix` stop with exit code 2 before any cluster when kind, helm or kubectl is missing, and `scan` needs helm only. CI tests with kind v0.33.0, Helm v4.3.0 and v3.22.0, and kubectl v1.37.1. `matrix` pins node images built for kind v0.33.

Prebuilt binaries for Linux and macOS, on amd64 and arm64, are attached to this release as `helmbulance_v0.1.0_<os>_<arch>.tar.gz`, with `SHA256SUMS` over them. Each archive has a build provenance attestation:

```sh
sha256sum --check --ignore-missing SHA256SUMS
gh attestation verify helmbulance_v0.1.0_linux_amd64.tar.gz --repo Git-Hospital/helmbulance
```

The archives are not signed with cosign and have no SBOM yet; both are planned for v0.2.

## Scenarios

`helmbulance test <chart>` runs these, or the ones named with `--scenario`:

| Scenario | What it does | Finding IDs |
|---|---|---|
| `upgrade-without-values` | Upgrades with reused values (control), then with the values files only, and compares the Secrets the release renders, and which workloads restart. | HB-UV-001 Secrets change on every upgrade, even with the same values; HB-UV-002 Secret values lost or changed when an upgrade leaves out an install-time `--set`; HB-UV-003 an upgrade that changes nothing restarts pods |
| `chart-upgrade` | Installs an earlier chart version (`--from-version`) and upgrades to the chart under test with the same values. | HB-CU-001 the upgrade fails; HB-CU-002 the new version changes or drops Secret values; HB-CU-003 workloads are not healthy after the upgrade |
| `zero-downtime` | Sends a light, steady stream of requests to the release's Service while its pods are replaced, one workload at a time, and counts the failures. | HB-ZD-001 requests fail while the pods are replaced |
| `reinstall` | Uninstalls and installs again with the same values, and checks volumes and Secrets. | HB-RI-001 data survives but its credentials do not; HB-RI-002 a surviving volume comes back without its data; HB-RI-003 the release does not install again; HB-RI-004 a Secret that outlives the uninstall is replaced |
| `gitops-render` | Renders the chart without a cluster, as Argo CD does, and finds Secrets that would change on every sync. | HB-GR-001 |

Two more commands:

- `helmbulance scan <chart>`: a static pre-screen, no cluster, seconds. It lists **candidates** (HB-SCAN-001 to HB-SCAN-006) and the `test` run that confirms each. It exits 0 on candidates. With `--strict` it exits 1 on a candidate and 3 when a check could not run. An interrupted scan exits 3 either way.
- `helmbulance matrix <chart>`: installs the chart on Kubernetes 1.34 to 1.37, one kind cluster per version. HB-K8S-001 does not install, HB-K8S-002 not healthy, HB-K8S-003 deprecated or removed APIs, HB-K8S-004 other API server warnings.

## Reports

`test`, `matrix` and `scan` write `report.md`, `report.json` and `report.sarif` to `--report-dir` (default `helmbulance-report`). Exit codes: 0 nothing found, 1 a finding, 2 a usage or setup error, 3 a scenario could not finish (INCONCLUSIVE).

## How the verdicts are checked

`testdata/verdicts.yaml` holds the cases whose right answer is known: a fixture chart with one defect, and its fixed twin. CI runs every case under Helm 3 and Helm 4 and fails on a missed finding, a finding on a fixed twin, or a changed verdict. Finding IDs that no pair covers yet are listed there under `uncovered`, with the reason. The [known-bug corpus](../corpus.md) holds released versions of public charts with known defects, and their fixed versions; D8 set the check on 8 November: at least 5 of the 6 known defects found, and no fixed version still showing the defect its fix addressed. The release checklist [#116](https://github.com/Git-Hospital/helmbulance/issues/116) runs the same check again on the release commit.

## Experimental

- **The GitHub Action.** It passes fewer options than the CLI, so it finds less: it has no `--set` input, so no install-only values and no HB-UV-002. It runs only `test`, on a Linux runner with Docker, with helm v4.3.0, and builds Helmbulance from its own source at the pinned commit rather than using the release archives. See [its limits](../github-action.md#status-experimental).

## Run only charts you trust

`test` and `matrix` install the chart into a kind cluster on your Docker host, and v0.1.0 has no protections for someone else's chart; they are planned for v0.3 ([architecture §4](../architecture.md)). Both refuse a repository, OCI or URL reference unless you pass `--allow-remote`, which then runs that chart without protections. The refusal catches mistakes and is not a protection: a local copy of a third-party chart, and its vendored `charts/` subcharts, run unprotected too. `scan` only renders the chart.

## Known limitations

Open issues that a v0.1.0 user can meet. Each one says what is still open:

- [#51](https://github.com/Git-Hospital/helmbulance/issues/51): HB-SCAN-003 reads the template source, so it misses some candidates and flags some guarded Secrets.
- [#54](https://github.com/Git-Hospital/helmbulance/issues/54): a workload that moves to a new credential key in an upgrade is named in the summary, not reported, and kubectl reads have no timeout of their own.
- [#55](https://github.com/Git-Hospital/helmbulance/issues/55): `docs/architecture.md` still describes parts that are not built, such as the failure bundle.
- [#60](https://github.com/Git-Hospital/helmbulance/issues/60): some finding IDs have no fixture pair yet; `testdata/verdicts.yaml` lists them under `uncovered`.
